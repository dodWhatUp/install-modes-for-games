## Build sequence and acceptance

Required comparison gate, added 2026-10-11: before rendering-performance or injected-feature cost runs, verify Dynamic MFG inactive and effective FG Off or one matched fixed multiplier using current native/global/per-game state and supported readback. Active/suspected/unverified adaptive FG or unknown effective FG blocks the run; native x2 selection is not sufficient. Match PT/SR/quality/scene/cache and validate rendered/displayed metrics and separate memory scopes. Memory warnings interrupt the run, not permission to silently lower textures or disable warnings. Explicit adaptive-FG experience studies remain separately labeled. Implement adapter/planner gate acceptance later; current documentation is not automatic runtime enforcement. See [mandatory preflight](GAME-PERFORMANCE-MEASUREMENT.md#mandatory-benchmark-preflight--fg-and-memory) and [Cyberpunk audit](../games/cyberpunk-2077/RUNTIME-VALIDATION.md#2026-10-11-interpretation-audit--effective-fg-mode-remains-unverified). Recording/game tests remain deferred.

1. **Capture contract and private archive.** Versioned run/phase/event schemas, UTC + QPC clock mapping, immutable files, hardware/settings/mod hashes, provenance and failure states. Store private paths/saves/raw logs outside Git. Acceptance: an interrupted capture remains readable and cannot overwrite the baseline.
2. **Minimal runner and resource imports.** Integrate existing programs for resident/private/system commit, adapter VRAM and supported CPU/GPU clocks/power/thermal/paging/I/O reports. Keep the initial PowerShell collector and its existing evidence as an interim prototype; do not expand it into a duplicate complex sensor engine. Acceptance: imported fields retain their source and units, unavailable values remain null, collection overhead is measured against matched control runs, and integration adds no clock/limiter changes or game injection.
3. **Frame capture and existing analysis programs.** Use validated capture/analysis programs to supply lows, percentiles, stutter information, latency and trace-loss diagnostics. A frame collector alone does not establish that these summary metrics are available. Import reports/exports with tool version, actual metric definition, sample count/duration, swapchain, frame class, phase and coverage where exposed. Keep the existing custom analyzer as a historical prototype, not the default metric provider. Acceptance: adapters match the source report, unsupported values remain unavailable, differently defined lows are not relabeled as equivalent, and rendered/displayed/unknown rates remain separate.
4. **Comparison and stability report.** Three-or-more comparable runs, ordered/randomized A/B/A comparisons when practical, settings equality checks, distributions and spread, crash/exit/device events, before/after memory growth and headroom. Acceptance: a different PT/SR/cache workload is explicitly flagged rather than sold as a mod speedup.
5. **Scenario runner.** Repeatable routes plus non-periodic/new-area runs, cold-start/first-visit/warm-revisit labels, load/alt-tab/resolution changes, and manual event markers. Guard all file/profile switches against a running game/store/launcher/compiler. Acceptance: no quest advancement or overwritten recovery saves, resumable checkpoints, validated rollback.
6. **Latency/visual integration.** Import supported Reflex/PC/display/input measurements from existing programs or supported measurement hardware, preserving endpoint and coverage definitions. Separate rotation, translation, HUD and animation scenarios. Later optical hardware/high-speed-video integration if requested; do not build a duplicate latency engine. Acceptance: no claim of physical camera/animation latency from FPS or a software counter alone; recording overhead calibrated.
7. **Cross-game profiles and sharing.** Portable metadata/config profiles, schema-migration tests and a local HTML report. Private raw evidence bundle to the user's Drive; sanitized docs/source/results to the canonical GitHub repository. Acceptance: no proprietary binaries, private paths, credentials, saves or full raw game logs in Git.

## Architecture choices

Build the coordinator, markers, schemas, import/normalization adapters, comparison/reporting and profile guards ourselves. Existing programs supply complex measurements and calculations; the helper preserves provenance and compares their reported values without reimplementing lows, latency, ETW decoding or complex sensor analysis. Keep adapters replaceable so the user can choose programs and workflows. Start with standard-library Python/PowerShell and no mandatory resident overlay, database or web server. Streaming CSV/JSON is enough initially. Add a UI only after the integration/data contract works.

Capture process CPU/memory and collection duration. Prefer persistent readers/batched calls over launching one program per sensor or repeated expensive WMI queries. Sample resources at an appropriate low frequency and events at native frame frequency. Keep optional heavyweight video/WPR traces for a reproducible anomaly. MSI Afterburner, RTSS and NVIDIA tools should remain optional data adapters when already configured, preserving their preconfigured baseline.
